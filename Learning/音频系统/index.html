链路 1：场景重载后为什么只有一个 AudioManager

重点掌握 
[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.BeforeSceneLoad)]
private static void Bootstrap() => EnsureInstance();

private void Awake()
{
    if (Instance != null && Instance != this)
    {
        Destroy(gameObject);
        return;
    }
    Instance = this;
    DontDestroyOnLoad(gameObject);
}

BeforeSceneLoad 保证业务对象开始工作前已有音频入口；DontDestroyOnLoad 让音乐和设置跨场景保留；重复检查避免某个场景手工放置管理器后产生双重播放。SubsystemRegistration 还会重置静态引用，兼容关闭 Domain Reload 的编辑器设置。

链路 2：为什么业务层只传 AudioCue

重点掌握 
AudioManager.PlaySfxAt(
    hitAnyTarget ? AudioCue.AttackHit : AudioCue.AttackSwing,
    transform.position);

攻击模块表达的是“命中”或“挥空”，而不是 knifeSlice2.ogg。素材更换、随机变体、默认音量和空间化策略都封装在管理器内。枚举相较字符串能避免拼写错误，并支持 IDE 查找引用。

取舍：枚举适合当前固定规模。大型项目若要热更新或让音频设计师独立配置，可改成带稳定 ID 的 ScriptableObject Event/Cue 资产。

链路 3：两个音乐声源怎样交叉淡化

重点掌握
当前 Music_A 播放 → 下一曲交给 Music_B，初始音量 0 → 同一段协程中：A 逐渐到 0，B 逐渐到目标音量 → 停止并清空 A → B 成为 activeMusicSource 下一次切换反过来使用 A

淡化用 Time.unscaledDeltaTime，因为战斗暂停和胜负结算会把 timeScale 设为 0；若使用普通 deltaTime，暂停期间协程会永远停在当前进度。

链路 4：为什么短音效使用声源池

重点掌握

攻击、受伤和爆炸可能在同一帧重叠。单个 AudioSource 会互相打断；每次创建 GameObject 又会产生生命周期和 GC 压力。系统启动时预建 12 个 AudioSource，播放时先找空闲声源；全部占用时轮转复用一个，保证资源上限可控。

空间音效

战斗音效设置 spatialBlend = 1，使用 3～18 米线性衰减，并把声源移动到事件发生位置。

全局音效

UI、胜负等使用 spatialBlend = 0，不因玩家与世界坐标距离而听不见。

每个 Cue 还可配置小幅随机 Pitch，并避免连续选择同一个攻击变体，降低重复感。

链路 5：音量设置怎样立即生效并跨启动保存

重点掌握
通道应用位置默认值
MasterAudioListener.volume100%
Music音乐 Cue 音量 × Music65%
SFX音效 Cue 音量 × SFX80%
Mute临时把 Listener 输出置 0，保留三个滑杆值关闭

暂停/结算面板包含三个滑杆；M 切换静音。变化先写入内存并立即应用，再写入 PlayerPrefs；应用暂停或退出时统一 Save。

局限：当前使用逻辑总线，没有 AudioMixer Snapshot、压缩器或滤波效果。需要战斗/菜单不同混音、低血量滤波或动态范围控制时，应升级为 AudioMixer 分组。

高频面试追问

1. 为什么 AudioManager 要跨场景存在？
避免切场景时音乐硬切和设置丢失，也让所有场景共享同一播放入口。代价是它拥有跨场景生命周期，必须防重复实例并正确解绑 sceneLoaded 事件。
2. 为什么不直接在每个角色上挂 AudioClip？
那会让业务 Prefab 同时承担素材配置，替换声音时要改大量对象。AudioCue 把“发生什么”与“播哪个文件”分开，统一处理音量、变体和空间策略。
3. PlayOneShot 不就能叠加吗，为什么还要池？
同一 AudioSource 的 OneShot 能叠加，但难以分别设置每次播放的位置、Pitch、停止策略与并发优先级。池让每个活动声音有独立声源，同时保持固定对象数量。
4. 12 个声源满了怎么办？
当前按轮转复用，这是 Demo 级可预测降级。生产项目会给 Cue 增加优先级和并发上限，优先淘汰远处、较旧或低优先级声音，并保留 UI 和关键反馈。
5. 为什么淡化使用 unscaledDeltaTime？
暂停和结算会把 timeScale 设为 0，普通 deltaTime 也变成 0，音乐淡化无法完成。音频界面属于真实时间体验，因此使用不受游戏时间影响的 unscaledDeltaTime。
6. Resources 有什么缺点？
自动包含目录内全部资源，按字符串路径加载，规模扩大后不利于依赖分析和按包更新。当前只有少量固定 Cue，换来零场景配置；后续可迁移到 ScriptableObject Library + Addressables。
7. 下一步如何升级？
加入 AudioMixer 的 Music/SFX/UI 分组与 Snapshot；Cue 配置资产化；添加优先级、并发限制、对象跟随和音效冷却；对脚步按材质选择 Clip；用 LUFS 测量统一响度。

60 秒项目介绍模板

“我为项目实现了一套跨场景音频系统。游戏逻辑不直接引用素材，而是发送 AudioCue，让 AudioManager 统一决定 Clip、随机变体、默认音量和空间化。管理器在场景加载前自动创建并用 DontDestroyOnLoad 保持唯一实例；音乐使用双 AudioSource 和 unscaledDeltaTime 做交叉淡化，短音效使用 12 个声源池支持并发。

系统提供 Master、Music、SFX 和静音控制，设置通过 PlayerPrefs 持久化。我把音效接到了攻击命中与挥空、受伤死亡、冲刺、两个技能、技能树、暂停和胜负流程。素材来自两套 CC0 资源，并记录了来源、许可和哈希。最后用 Unity Play Mode 冒烟测试逐个验证 AudioCue 能加载，同时复测战斗闭环。当前的主要演进方向是 AudioMixer Snapshot、Cue 资产化和声音优先级。”
